# Database schema snapshot (source of truth for review)

This folder is the **human-reviewable record of the database's security posture** for
the KJST RFP platform. The live schema and Row-Level Security (RLS) policies are managed
in the hosted Supabase project (via the Supabase MCP), which historically meant they could
not be diffed, code-reviewed, or shown to a client's security reviewer. These files close
that gap: they are a committed snapshot that answers the question "prove one hotel cannot
read another hotel's bid" with actual policy text.

## Files

- **`schema_snapshot.sql`** — the full snapshot, in three sections:
  1. **Tables** — every table in `public` with its columns.
  2. **Row-Level Security** — `enable row level security` on all 27 tables, plus all 61
     `create policy` statements. This is the data-isolation guardrail from CLAUDE.md,
     made explicit and auditable.
  3. **Security-definer functions** — the 12 `SECURITY DEFINER` functions the RLS policies
     depend on (`current_org_id()`, `is_admin()`, `is_timeline_admin()`, etc.). RLS is only
     as trustworthy as these, so they are captured too.

## How the isolation works (the one-paragraph version for a reviewer)

Every tenant table is scoped to the caller's organization through
`organization_id = current_org_id()`, where `current_org_id()` reads the org off the
signed-in user's profile. Child tables (responses, answers, invitations) inherit that scope
by joining back up to `clients`. Hotels are never signed in — they reach exactly one
invitation through an unguessable 192-bit token, and the public edge functions filter by
that token with the service role. All 27 tables have RLS enabled; there are no
`using (true)` tenant-data policies.

## Refreshing this snapshot

It was generated by introspecting the live database (`pg_policies`, `pg_get_functiondef`,
`information_schema`). Regenerate it after any schema or policy change so the committed copy
stays honest. A full, migration-grade dump can also be produced with
`supabase db pull --linked -p <db-password>` (the password lives in the backup workflow's
secrets), which writes a replayable migration under `supabase/migrations/`.

> This is a snapshot for review, not a migration history. The nightly backup
> (`TeamCYMBUL/kjst-rfp-backups`) remains the disaster-recovery copy of schema **and** data.
